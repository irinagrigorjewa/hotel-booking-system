# 1. Scope — границы продукта (MVP)

## Назначение раздела

Раздел **Scope** фиксирует, что входит в минимально жизнеспособный продукт (MVP) Hotel Booking System, что сознательно исключено, каковы границы системы и критерии готовности на уровне продукта.

Документ предназначен для разработчиков, тимлида и ревьюеров: по нему проверяют, что задача относится к MVP, не раздувает объём и не подменяет другие разделы спецификации (доменная модель, API, UI). Здесь описываются **продуктовые границы и зависимости модулей**, а не контракты эндпоинтов, схемы БД или макеты экранов.

**Продукт:** веб-приложение для поиска отелей и бронирования номеров.  
**Стек MVP:** React 19 + TypeScript + Vite (frontend), FastAPI + SQLAlchemy 2 + PostgreSQL (backend), Docker Compose, GitHub Actions.

---

## 2. Цели MVP (product goals)

| # | Цель | Как измеряется в MVP |
|---|------|----------------------|
| G1 | Клиент может зарегистрироваться, войти и безопасно работать в сессии | Регистрация, login, refresh, logout; роли `CLIENT` / `ADMIN` |
| G2 | Админ может вести каталог отелей и номеров | CRUD отелей, типов номеров, номеров; загрузка фото; координаты для карты |
| G3 | Клиент находит подходящий номер | Поиск по городу, фильтры (цена, вместимость, даты доступности) |
| G4 | Клиент оформляет и управляет бронью | Создание с проверкой пересечений и расчётом цены; просмотр; отмена своих броней |
| G5 | Каталог «живой»: отзывы, избранное, карта, мультиязычность | Отзывы и рейтинг, избранное, карта с маркерами, UI `ru`/`en` |
| G6 | Админ контролирует платформу | Пользователи (роль), каталог, все бронирования, модерация отзывов |
| G7 | Проект воспроизводим и проверяем | Docker Compose, CI (линтеры, тесты, сборка, образы), README + `.env.example` |

**Не является целью MVP:** монетизация (платежи), маркетинг-коммуникации (email/push), BI и отчётность, автоматический геокодинг адресов.

## 3. In Scope — детализация

Ниже каждый пункт MVP разобран по шаблону: **что входит**, **зачем**, **границы**, **зависимости**.

### 3.1. Регистрация и JWT-аутентификация (access + refresh)

| | |
|---|---|
| **Что входит** | Регистрация пользователя; вход с выдачей пары access + refresh; обновление access через refresh (rotation); logout с инвалидацией refresh; две роли: `CLIENT`, `ADMIN`. |
| **Зачем** | Базовый контур безопасности и разграничения прав; без него невозможны бронирования, избранное, отзывы и админка. |
| **Границы** | Нет email-подтверждения, сброса пароля, OAuth/SSO, 2FA, управления сессиями «со всех устройств» как отдельного UI. Хранение и TTL токенов — по правилам auth в доменном разделе; детали API — в API-контракте. |
| **Зависимости** | Сущности User, RefreshToken; все защищённые сценарии клиента и админа. |

### 3.2. CRUD отелей, типов номеров, номеров (админ)

| | |
|---|---|
| **Что входит** | Создание, чтение, обновление, удаление отелей (включая город, адрес, описание, звёзды, lat/lng); справочник типов номеров; номера с ценой за ночь, вместимостью, статусом (`AVAILABLE` / `MAINTENANCE`). Запрет удаления отеля/номера при активных бронях. |
| **Зачем** | Формирует каталог, без которого поиск, карта, бронирование и отзывы бессмысленны. |
| **Границы** | Нет мультиязычного контента каталога (переводится только UI); нет мульти-отельных сетей, тарифов по сезонам, доп. услуг (завтрак и т.п.); нет массового импорта. |
| **Зависимости** | Auth (роль ADMIN); Booking (блокировка удаления); Image (фото); Map (координаты); Search/Filters (город, цена, capacity). |

### 3.3. Поиск отелей по городу и фильтры номеров

| | |
|---|---|
| **Что входит** | Публичный просмотр списка отелей с поиском/фильтрацией по городу и пагинацией; фильтрация номеров по цене, вместимости и диапазону дат (доступность с учётом броней). Карточка отеля: описание, фото, номера, отзывы, рейтинг, карта. |
| **Зачем** | Основной клиентский путь «найти → выбрать → забронировать». |
| **Границы** | Нет полнотекстового поиска, автодополнения городов, фильтров по удобствам/звёздам как отдельного обязательного MVP-набора (если не оговорено иначе в UI/API); нет рекомендаций и «похожих отелей». Геокодинг адреса в поиск не входит. |
| **Зависимости** | Hotel, Room, Booking (занятость по датам); Image, Review (обогащение карточки); i18n (подписи фильтров). |

### 3.4. Создание бронирования

| | |
|---|---|
| **Что входит** | Создание брони на номер с `check_in` / `check_out`; проверка пересечения дат с активными бронями; расчёт `total_price` по правилам домена (exclusive checkout, лимиты ночей и т.д.); атомарность создания (конкурентный доступ). |
| **Зачем** | Ядро бизнес-ценности продукта. |
| **Границы** | Нет оплаты, холда карты, промокодов, групповых броней, изменения дат после создания (кроме отмены), waitlist. Статусы и инварианты — в доменной модели, не дублируются здесь. |
| **Зависимости** | Auth (CLIENT+); Room (AVAILABLE); правила пересечений Booking; косвенно Admin (просмотр всех броней). |

### 3.5. Просмотр и отмена своих бронирований (клиент)

| | |
|---|---|
| **Что входит** | Список своих броней; отмена активной (`PENDING` / `CONFIRMED`) → `CANCELLED`. |
| **Зачем** | Замыкает цикл self-service клиента после создания брони. |
| **Границы** | Нет перебронирования, частичной отмены, штрафов, уведомлений об отмене. Админская смена статуса — в админ-панели, не в клиентском кабинете. |
| **Зависимости** | Booking create; Auth; Admin bookings (симметричный контроль). |

### 3.6. Загрузка и отображение фото отелей и номеров

| | |
|---|---|
| **Что входит** | Админ загружает / удаляет / упорядочивает фото; клиент и гости видят галерею в карточке отеля/номера. Хранение файлов на диске (volume), отдача через static/media. Ограничения формата/размера/количества — по доменным правилам. |
| **Зачем** | Визуальное доверие к каталогу; обязательный элемент карточки. |
| **Границы** | Нет CDN, image CDN transforms, видео, 360°, внешних object storage (S3) как обязательного требования MVP; нет модерации фото отдельным workflow. |
| **Зависимости** | Admin CRUD Hotel/Room; карточка отеля (поиск/просмотр); Docker volume для `uploads/`. |

### 3.7. Отзывы и рейтинг отелей

| | |
|---|---|
| **Что входит** | Аутентифицированный пользователь оставляет один отзыв на отель (рейтинг 1–5 + текст); редактирование/удаление своего отзыва; агрегированный рейтинг и счётчик на отеле; админ удаляет любой отзыв (модерация). |
| **Зачем** | Социальное доказательство и сигнал качества для поиска. |
| **Границы** | Нет обязательной привязки «только после проживания», ответов отеля, фото в отзыве, жалоб от пользователей, ранжирования ленты. |
| **Зависимости** | Auth; Hotel; Admin moderation; карточка отеля / список (avg_rating). |

### 3.8. Карта с маркерами отелей

| | |
|---|---|
| **Что входит** | Отображение карты (Map library на фронтенде) с маркерами по `latitude` / `longitude` отеля; координаты задаёт админ вручную при CRUD. |
| **Зачем** | Пространственный контекст локации без бэкенд-геокодинга. |
| **Границы** | Нет геокодинга адресов на бэкенде, маршрутов, кластеризации как обязательного требования, поиска «рядом со мной» по GPS пользователя (если не добавлено явно позже). Выбор конкретной библиотеки — решение реализации, не расширение scope. |
| **Зависимости** | Hotel (lat/lng required для карты); Admin CRUD; карточка / список отелей. |

### 3.9. Избранные отели

| | |
|---|---|
| **Что входит** | Добавить / убрать отель из избранного; список избранного; признак `is_favorite` в списках для авторизованного пользователя. |
| **Зачем** | Удержание и ускорение повторного выбора без бронирования. |
| **Границы** | Нет шаринга списков, папок, уведомлений о изменении цены, избранного для гостя без аккаунта. |
| **Зависимости** | Auth; Hotel; список/карточка отелей. |

### 3.10. i18n: русский и английский

| | |
|---|---|
| **Что входит** | Переключение языка UI `ru` / `en`; сохранение выбора (например localStorage); локализация интерфейсных строк (кнопки, формы, сообщения ошибок UI-уровня). |
| **Зачем** | Два целевых языка продукта с первого релиза. |
| **Границы** | Нет локализации пользовательского/админского контента (названия отелей, описания, отзывы); нет RTL, нет других локалей; нет серверного Accept-Language как обязательного источника истины. |
| **Зависимости** | Все UI-экраны клиента и админки; не блокирует backend-домен. |

### 3.11. Админ-панель

| | |
|---|---|
| **Что входит** | Управление пользователями (просмотр, смена роли) с защитой от снятия роли у себя / удаления единственного админа; CRUD отелей и номеров; просмотр всех бронирований и смена статуса; модерация отзывов (удаление); управление фото. |
| **Зачем** | Операционное управление платформой без прямого доступа к БД. |
| **Границы** | Нет audit log UI, bulk-операций, кастомных ролей, RBAC мельче ADMIN/CLIENT, аналитических дашбордов. |
| **Зависимости** | Auth (ADMIN); все админские CRUD и модерация; Booking, Review, User, Image. |

### 3.12. Docker Compose

| | |
|---|---|
| **Что входит** | Локальный/демо-запуск связки frontend + backend + PostgreSQL; volume для загрузок; переменные окружения через `.env` / `.env.example`. |
| **Зачем** | Единый способ поднять систему у разработчика и для демонстрации. |
| **Границы** | Нет Kubernetes, multi-node prod orchestration, managed cloud DB как части MVP-поставки; прод-хардening (TLS termination и т.п.) — вне минимального scope, если не оговорено отдельно в ops-разделе. |
| **Зависимости** | Frontend, backend, PostgreSQL, uploads; README с инструкцией запуска. |

### 3.13. CI (GitHub Actions)

| | |
|---|---|
| **Что входит** | Пайплайн: линтеры, тесты, сборка приложения, сборка Docker images. |
| **Зачем** | Контроль качества и воспроизводимость перед merge. |
| **Границы** | Нет обязательного CD на прод, canary, security scanning как must-have MVP (можно добавить позже без смены продуктового scope каталога). |
| **Зависимости** | Исходный код фронта/бэка; Dockerfile’ы; тестовый набор. |

### 3.14. README + `.env.example`

| | |
|---|---|
| **Что входит** | Документация запуска, стека, основных команд; пример переменных окружения без секретов. |
| **Зачем** | Онбординг разработчика и проверяемость демо. |
| **Границы** | Не заменяет разделы спецификации (Scope, домен, API, UI); не включает продакшен runbook. |
| **Зависимости** | Compose, CI, seed-данные при первом запуске (описаны в домене). |

### Сводка зависимостей модулей (MVP)

```text
Auth ──► Booking, Favorites, Reviews, Admin
Hotel/Room CRUD ──► Search, Map, Photos, Booking, Reviews, Favorites
Booking rules ──► Search (date filters), Admin bookings, Delete guards
Photos ──► Hotel/Room cards
Reviews ──► Hotel cards + Admin moderation
Map ──► Hotel lat/lng (admin-entered)
i18n ──► все UI-экраны
Compose/CI/README ──► воспроизводимость всего MVP
```

## 4. Out of Scope — детализация

| Исключено | Почему не в MVP | Возможные future extensions |
|-----------|-----------------|-----------------------------|
| **Email / восстановление пароля** | Усложняет инфраструктуру (SMTP, шаблоны, токены сброса, безопасность ссылок) без необходимости для демо каталога и броней. | Verify email; forgot/reset password; transactional mail (подтверждение брони). |
| **Платежи** | Требуют провайдера, PCI-ограничений, вебхуков, сверки статусов оплаты vs брони; отдельный продуктовый контур. | Checkout, холд/charge, возвраты, счета. |
| **Аналитика, экспорт Excel/PDF** | Не нужны для доказанного happy-path бронирования; BI отвлекает от ядра. | Админ-дашборд, выгрузки броней/отзывов, отчёты за период. |
| **Push-уведомления** | Нужны PWA/FCM/APNs, согласие пользователя, сервер рассылок. | Напоминания о заезде, смена статуса брони, ответы на отзывы. |
| **Геокодинг адресов на бэкенде** | Внешние API, квоты, неоднозначность адресов; для MVP достаточно ручных координат админа. | Автозаполнение lat/lng по адресу; reverse geocoding; поиск по радиусу. |

**Также вне scope по умолчанию** (следствие границ выше, не отдельный backlog MVP): чат с отелем, мультивалютность, календарь цен по датам, мобильные native-приложения, мультитенантность white-label.

## 5. Границы системы

### Система делает

- Ведёт учёт пользователей с ролями CLIENT и ADMIN и аутентифицирует их через JWT (access + refresh).
- Даёт админу управлять каталогом отелей, типов номеров, номеров и фотографий; задавать координаты вручную.
- Позволяет анонимно и авторизованно просматривать каталог, искать по городу, фильтровать номера (в т.ч. по датам доступности).
- Создаёт бронирования с проверкой пересечений и расчётом стоимости; показывает клиенту его брони и позволяет отменять активные.
- Поддерживает отзывы с рейтингом, избранное, карту маркеров, переключение языка UI.
- Даёт админу обзор пользователей, броней и модерацию отзывов.
- Запускается через Docker Compose и проверяется CI; сопровождается README и `.env.example`.

### Система не делает

- Не принимает и не проводит платежи; бронь в MVP не связана с оплатой.
- Не отправляет email/SMS/push и не восстанавливает пароль по почте.
- Не геокодирует адреса и не гарантирует точность координат сверх данных, введённых админом.
- Не строит аналитику, отчёты и файловые экспорты для бизнеса.
- Не является channel manager / PMS полной гостиничной автоматизации (housekeeping, тарифные сетки, каналы продаж OTA).
- Не локализует пользовательский контент каталога — только строки интерфейса.

### Внешние границы ответственности

| Зона | В MVP | Вне MVP |
|------|-------|---------|
| Данные координат | Ручной ввод админом | Геокодинг-провайдер |
| Файлы фото | Локальный volume / static | Обязательный облачный object storage |
| Карта | Клиентская Map library + ключи провайдера карты (если нужны) | Серверный рендеринг тайлов |
| Секреты | `.env` / CI secrets | Vault / cloud secret manager как must-have |

## 6. Предположения и ограничения (assumptions & constraints)

### Предположения (assumptions)

1. Один логический деплоймент / один «оператор» платформы: нет изоляции данных между сетями отелей.
2. Аудитория MVP — демонстрация и учебный/продуктовый протокол: seed-пользователи и seed-каталог допустимы и ожидаемы.
3. Админ корректно задаёт lat/lng; карта отображает то, что сохранено, без валидации «адрес ↔ координаты».
4. Клиент и админ работают через веб-браузер; мобильная вёрстка — адаптивная веб, не native.
5. Язык контента отелей/отзывов — как ввёл пользователь/админ; i18n не переводит эти тексты.
6. Время для правил бронирования опирается на договорённости домена (в т.ч. UTC для «сегодня»); TZ-политика не расширяет scope отдельным продуктовым модулем.
7. Access и refresh в MVP могут храниться на клиенте согласованно с правилами auth; httpOnly cookie для refresh допустим как вариант реализации, не как отдельная фича scope.

### Ограничения (constraints)

| Тип | Ограничение |
|-----|-------------|
| **Технологический** | Зафиксированный стек: React 19 + TS + Vite; FastAPI + SQLAlchemy 2 + PostgreSQL; Compose; GitHub Actions. |
| **Ролевая модель** | Только `CLIENT` и `ADMIN`; нет промежуточных ролей. |
| **Бронь** | Без оплаты; статусы и пересечения — по доменным правилам; лимит длительности проживания (домен). |
| **Медиа** | Локальное файловое хранилище; лимиты формата/размера/количества фото. |
| **Отзывы** | Один отзыв на пару пользователь–отель. |
| **i18n** | Только `ru` и `en` для UI. |
| **Интеграции** | Нет платёжных, email, push, геокодинг API в обязательном контуре. |
| **Безопасность MVP** | JWT HS256 / opaque refresh с hash в БД — по спецификации; полноценный security audit / penetration test не входит в definition of done Scope. |

## 7. Критерии готовности Scope (Definition of Done — продукт)

Scope MVP считается закрытым, когда выполнены **все** пункты:

### Продуктовые сценарии

- [ ] Новый пользователь регистрируется и входит; получает рабочую сессию с refresh; может выйти.
- [ ] CLIENT: поиск отелей по городу, фильтры номеров, карточка с фото/отзывами/рейтингом/картой.
- [ ] CLIENT: создание брони с корректной ценой и отказом при пересечении дат; список своих броней; отмена активной.
- [ ] CLIENT: избранное; свой отзыв (создать/изменить/удалить); переключение `ru`/`en` с сохранением выбора.
- [ ] ADMIN: CRUD отелей (с координатами), типов номеров, номеров; фото; нельзя удалить сущность с активными бронями.
- [ ] ADMIN: список пользователей и смена роли (с защитой единственного админа); все бронирования и смена статуса; удаление чужого отзыва.

### Воспроизводимость и качество поставки

- [ ] `docker compose up` поднимает frontend, backend, PostgreSQL; есть seed-данные для демо.
- [ ] CI зелёный: линтеры, тесты, сборка, Docker images.
- [ ] README описывает запуск; `.env.example` покрывает необходимые переменные без секретов.

### Соответствие границам

- [ ] В поставке нет реализации out-of-scope как «обязательных» модулей (платежи, email reset, геокодинг, push, аналитика/экспорт).
- [ ] Расхождения с другими разделами спецификации (домен/API/UI) зафиксированы и согласованы; Scope не подменён скрытым расширением.

## 8. Риски scope creep

| Риск | Симптом | Как держать в границах |
|------|---------|------------------------|
| «Почти платежи» | Статусы вроде `PAID`, интеграция тестового эквайринга «на 1 день» | Оплата = отдельный эпик; бронь остаётся без платёжного контура |
| «Раз уж JWT» | Email verify, reset, magic link, OAuth | Явно out of scope; заводить future issue, не тащить в MVP |
| «Карта должна искать сама» | Геокодинг, places autocomplete, «рядом со мной» | Координаты только ручные; карта = отображение маркеров |
| «Админке не хватает отчётов» | Excel/PDF, графики загрузки | Аналитика out of scope; хватает списков и смены статусов |
| «Контент тоже на двух языках» | Поля `name_ru`/`name_en`, админка переводов | i18n = только UI-строки |
| «Фото как в проде» | S3, CDN, ресайзы, watermark | Volume + лимиты MVP; облако — later |
| «Уведомим хоть как-нибудь» | SMTP «временно», telegram-бот | Коммуникации out of scope до отдельного решения |
| Размытие ролей | Manager, Moderator, Owner | Только CLIENT/ADMIN; модерация отзывов = право ADMIN |
| Перенос домена в Scope | Дублирование формул цены, SQL, DTO | Scope ссылается на модули; детали — в домене/API/UI |
| «Ещё один фильтр» | Удобства, рейтинг, звёзды без лимита | Новые фильтры — только через изменение спецификации, не «заодно» |

### Правило управления изменениями scope

1. Любое добавление сверх списков In/Out Scope — отдельное решение (issue/ADR), не «мелкий PR».
2. Уточнение *как* реализовать уже включённый пункт (библиотека карты, cookie vs localStorage) — не scope creep.
3. Уточнение, которое добавляет новый актор, канал связи, деньги или внешний API — scope creep, пока не утверждено.

| В MVP | Не в MVP |
|-------|----------|
| Auth JWT + роли, каталог, поиск/фильтры, бронь, свои брони, фото, отзывы, карта, избранное, i18n UI, админка, Compose, CI, README | Email/reset, платежи, аналитика/экспорт, push, геокодинг |

**Владелец границ:** продуктовая спецификация (этот раздел). При конфликте «удобно добавить» vs Scope — приоритет у зафиксированных In/Out списков до явного пересмотра.
