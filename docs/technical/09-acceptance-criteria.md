# 9. Acceptance criteria

Документ задаёт **критерии приёмки (AC)** MVP Hotel Booking System: что должно быть доказано перед релизом или демо, как это проверять и при каких условиях решение — **go** или **no-go**.

Источник формулировок: спецификация проекта (`DESC.md`, раздел 9) и связанные use cases (UC-01…UC-20), правила домена, план поставки (этапы 1–10).

---

## 9.1. Как использовать AC

### Назначение

| Контекст | Цель |
|----------|------|
| **Перед релизом** | Подтвердить, что MVP готов к merge в `developer` / `main` и к эксплуатации на стенде Compose |
| **Demo / защита** | Пройти чеклист на живом стенде за ограниченное время; показать ключевые инварианты |
| **Регрессия** | После крупных изменений (auth, bookings, uploads) быстро убедиться, что критичные AC не сломаны |

### Порядок проверки

1. **Поднять стенд:** `docker compose up --build` (AC-11). Дождаться healthy backend, frontend, Postgres; volume `uploads` смонтирован.
2. **Seed:** убедиться, что доступны `admin@example.com` / `Admin123!` и `client@example.com` / `Client123!`, ≥ 2 отеля с lat/lng, номера, seed-фото, ≥ 1 отзыв.
3. **Ops / качество:** CI на PR зелёный (AC-12), coverage ≥ 80% (AC-13), README достаточен (AC-14) — можно частично параллельно со стендом.
4. **Критичные инварианты (обязательны для go):** auth/refresh (AC-02), overlap бронирований (AC-03), 409 при удалении с активными бронями (AC-10), изоляция броней по ролям (AC-09).
5. **Функциональный обход UC:** AC-01 (все UC-01…UC-20 на стенде), затем фото, отзывы, избранное, карта, i18n (AC-04…AC-08).
6. **Зафиксировать результат:** чеклист §9.3; решение go / no-go по §9.4. Out of scope (§9.5) **не** блокирует приёмку.

### Роли и артефакты

| Роль | Действия |
|------|----------|
| Проверяющий | Выполняет шаги AC, отмечает чеклист, фиксирует дефекты |
| Разработчик | Предоставляет стенд, Swagger `/docs`, логи Compose, отчёт coverage, ссылку на зелёный CI |
| Артефакты | Compose-стенд, seed-учётки, PR с зелёным CI, coverage report, README |

### Уровни доказательств

| Уровень | Когда достаточно |
|---------|------------------|
| **Автотест / CI** | AC-02 (частично), AC-03 (в т.ч. параллель), AC-10, AC-12, AC-13 |
| **Ручная проверка на стенде** | UC-сценарии UI (AC-01), карта (AC-07), i18n (AC-08), README (AC-14) |
| **Комбинация** | Фото (AC-04), отзывы (AC-05), избранное (AC-06), изоляция броней (AC-09) |

### AC-02. Access / refresh / logout

| Поле | Содержание |
|------|------------|
| **Формулировка** | Access-токен истекает по TTL; `POST /auth/refresh` выдаёт **новую пару** access+refresh (rotation, старый refresh revoked); отозванный или уже использованный refresh → `401`; `POST /auth/logout` инвалидирует переданный refresh. |
| **Тип** | Функциональный |
| **Как проверить** | **Автотесты (предпочтительно):** suite auth — login, refresh rotation, revoked refresh, logout. **Вручную / curl:** 1. Login → сохранить пару. 2. `POST /auth/refresh` с refresh → новая пара, старый refresh больше не работает. 3. Logout с актуальным refresh → последующий refresh → `401`. 4. (Опционально) укоротить `ACCESS_TOKEN_EXPIRE_MINUTES` на стенде и убедиться, что frontend делает один retry через refresh при 401. |
| **Ожидаемый результат** | Rotation соблюдена; revoked → `401`; после logout refresh недействителен; access без валидного токена на protected → `401`. |
| **Связь с UC** | UC-02 |
| **Этапы поставки** | Этап 2; регрессия на этапе 10 |

### AC-03. Запрет двойного бронирования (в т.ч. параллельно)

| Поле | Содержание |
|------|------------|
| **Формулировка** | Для одного `room_id` невозможно создать две брони со статусами `PENDING`/`CONFIRMED` с пересекающимися интервалами (`existing.check_in < new.check_out AND new.check_in < existing.check_out`). Правило держится при **параллельных** запросах (транзакция + `SELECT … FOR UPDATE` или эквивалент). |
| **Тип** | Функциональный |
| **Как проверить** | 1. **Последовательно:** создать бронь room X на 10–15; попытка 12–18 / 09–11 / 13–14 → `409` (или 400 по контракту проекта, но конфликт однозначен); 01–09 и 15–20 → успех. 2. **Параллельно:** два одновременных `POST /bookings` на один room и пересекающиеся даты (скрипт/`xargs -P`/тест с concurrent clients) → ровно одна успешная, вторая — конфликт. 3. После `CANCELLED`/`COMPLETED` пересечение снова разрешено. |
| **Ожидаемый результат** | Нет двух активных пересекающихся броней на один номер; параллельный race не даёт оба `2xx`. |
| **Связь с UC** | UC-06, UC-15 (косвенно — целостность календаря) |
| **Этапы поставки** | Этап 6; покрытие в этапе 10 |

### AC-04. Загрузка и отображение фото; невалидный файл → 4xx

| Поле | Содержание |
|------|------------|
| **Формулировка** | ADMIN загружает фото отеля и номера (`multipart`); файлы доступны в UI (список/карточка/галерея); невалидный файл (MIME, размер и т.п.) отклоняется с **4xx** (`413` / `415` / `400` / `422` по правилам API). |
| **Тип** | Функциональный |
| **Как проверить** | 1. Под ADMIN: `POST /hotels/{id}/images` и `POST /rooms/{id}/images` с JPEG/PNG в лимите. 2. Открыть публичную карточку отеля/номера — изображения видны (URL через backend/static). 3. Загрузить `.exe` / `text/plain` / файл сверх лимита → 4xx, запись Image не создаётся. 4. Delete/sort (UC-19) — опционально в том же прогоне. |
| **Ожидаемый результат** | Валидные фото в UI; невалидные → 4xx без записи в БД/диске (или с откатом); volume `uploads` содержит принятые файлы. |
| **Связь с UC** | UC-19, UC-04 |
| **Этапы поставки** | Этап 5; UI-галерея + этап 10 |

### AC-05. Один отзыв на отель; `avg_rating` в списках

| Поле | Содержание |
|------|------------|
| **Формулировка** | Аутентифицированный клиент может оставить **не более одного** отзыва на отель; повторный `POST` → конфликт/ошибка валидации; `avg_rating` (и при наличии `reviews_count`) отображается в `GET /hotels`, `GET /hotels/{id}` и в UI списков/карточки. |
| **Тип** | Функциональный |
| **Как проверить** | 1. CLIENT: `POST /hotels/{id}/reviews` `{ rating, comment }` → 201. 2. Повторный POST того же user+hotel → 409 (или эквивалент). 3. `GET /hotels` — у отеля обновлённый `avg_rating`. 4. UI: список и карточка показывают рейтинг. 5. PATCH/DELETE своего отзыва (UC-17) — avg пересчитывается. |
| **Ожидаемый результат** | Unique constraint/бизнес-правило «один отзыв»; avg согласован с данными Review. |
| **Связь с UC** | UC-17; отображение в UC-03, UC-04 |
| **Этапы поставки** | Этап 7 |

### AC-06. Избранное только для auth

| Поле | Содержание |
|------|------------|
| **Формулировка** | `GET /favorites`, `POST /favorites/{hotel_id}`, `DELETE /favorites/{hotel_id}` доступны только с валидным access; без токена → `401`. Add / remove / list работают для авторизованного пользователя; в списке отелей для auth — флаг `is_favorite`. |
| **Тип** | Функциональный |
| **Как проверить** | 1. Без `Authorization`: favorites endpoints → `401`. 2. С токеном CLIENT: POST → в списке favorites; DELETE → убран; повторный POST того же → 409 (или согласованный контракт). 3. UI: кнопка «в избранное» / страница избранного. |
| **Ожидаемый результат** | Гость не управляет избранным; auth-пользователь видит консистентный list и `is_favorite`. |
| **Связь с UC** | UC-16 |
| **Этапы поставки** | Этап 7 |

Клик по маркеру → навигация на детальную карточку того же `id`. 4. Мини-карта на деталях (если реализована) — координаты совпадают. |

### AC-09. Изоляция бронирований по ролям

| Поле | Содержание |
|------|------------|
| **Формулировка** | CLIENT в `GET /bookings` видит **только свои** бронирования; ADMIN видит **все**. Доступ к чужой брони по id для CLIENT → `403`/`404` (по контракту); ADMIN — доступен. |
| **Тип** | Функциональный |
| **Как проверить** | 1. Создать брони от client A и (при наличии) другого клиента / admin-created. 2. Login A → list только его id. 3. Login ADMIN → list содержит брони всех пользователей. 4. UI: `/bookings` vs `/admin/bookings`. |
| **Ожидаемый результат** | Нет утечки чужих броней клиенту; админ видит полный список. |
| **Связь с UC** | UC-07, UC-14 |
| **Этапы поставки** | Этап 6 (list client); этап 10 (admin bookings) |

### AC-10. Удаление отеля/номера с активными бронями → 409

| Поле | Содержание |
|------|------------|
| **Формулировка** | `DELETE /hotels/{id}` и `DELETE /rooms/{id}` при наличии связанных броней со статусом `PENDING` или `CONFIRMED` возвращают **409 Conflict**; сущность не удаляется. |
| **Тип** | Функциональный |
| **Как проверить** | 1. Создать `CONFIRMED` бронь на room. 2. ADMIN: DELETE room → `409`. 3. DELETE hotel этого room → `409`. 4. Cancel бронь → DELETE снова возможен (если нет других активных). Автотест на правило 10 домена. |
| **Ожидаемый результат** | HTTP 409; запись Hotel/Room остаётся в БД. |
| **Связь с UC** | UC-15 |
| **Этапы поставки** | Этап 6 (правило вместе с bookings); CRUD hotels/rooms — этапы 3–4 |

### AC-11. Docker Compose поднимает полный стек

| Поле | Содержание |

| **Формулировка** | Команда `docker compose up --build` поднимает **frontend**, **backend**, **PostgreSQL** и volume для **uploads**; миграции Alembic применяются на старте backend; сервисы доступны по URL из README. |

Проверить: Postgres accepting connections; backend health/`/docs`; frontend отдаёт SPA; запись файла upload попадает в volume и отдаётся по URL. |
| **Ожидаемый результат** | Три сервиса Up; uploads персистятся в volume; стенд готов к AC-01…AC-10 без ручной установки Postgres/Node на хосте. |

## 9.4. Критерии go / no-go

### Go (можно принимать MVP)

Выполнены **все** условия:

1. **AC-11** — стенд Compose поднимается и стабилен для демо.
2. **AC-01** — все UC-01…UC-20 воспроизведены на этом стенде (чеклист §9.3 закрыт).
3. **Обязательные инварианты без дефектов severity ≥ High:**
   - AC-02 (auth/refresh/logout)
   - AC-03 (overlap, включая параллельный сценарий)
   - AC-09 (изоляция броней)
   - AC-10 (409 при удалении)
4. **AC-04…AC-08** — приняты (допустимы только Low-дефекты UI/копирайта, не ломающие сценарий).
5. **AC-12** — CI на целевом PR зелёный.
6. **AC-13** — coverage ≥ 80%.
7. **AC-14** — cold start по README успешен.
8. Нет открытых дефектов по **in scope** MVP, блокирующих demo (5xx на happy path, потеря данных, обход ролей).

### No-go (приёмка отклоняется)

Любое из ниже:

| Условие | Пример |
|---------|--------|
| Compose не поднимает стек | AC-11 fail |
| Любой UC из UC-01…UC-20 не проходит | AC-01 fail |
| Сломан auth/refresh/logout | AC-02 fail |
| Возможны overlapping CONFIRMED/PENDING (в т.ч. race) | AC-03 fail |
| CLIENT видит чужие брони / ADMIN не видит все | AC-09 fail |
| Удаление hotel/room с активной бронью не даёт 409 | AC-10 fail |
| CI красный на PR | AC-12 fail |
| Coverage < 80% | AC-13 fail |
| README не позволяет запуск с нуля | AC-14 fail |
| Критичный UX MVP недоступен | нет фото при валидной загрузке; карта без маркеров; i18n не переключает основные экраны; избранное/отзывы ломают happy path (AC-04…AC-08 High) |

### Условный go (только по явному согласованию заказчика)

Допустимо **только** если задокументировано письменно:

- Косметические баги i18n (непереведённые редкие строки) при рабочем переключателе.
- Некритичная сортировка фото / UX админки.
- Известный Low по браузеру вне Chrome/Firefox/Safari.

Условный go **запрещён** для AC-02, AC-03, AC-09, AC-10, AC-11, AC-12, AC-13.

## 9.5. Известные исключения (out of scope — не проверять)

Следующее **не входит** в MVP и **не** является основанием для no-go, даже если отсутствует:

| Исключение | Комментарий |
|------------|-------------|
| Email / восстановление пароля | Нет писем, reset-flow, verify email |
| Платежи | Нет эквайринга, холдов, инвойсов |
| Аналитика, экспорт Excel/PDF | Нет дашбордов и выгрузок |
| Push-уведомления | Нет web-push / mobile push |
| Геокодинг адресов на бэкенде | Координаты задаёт админ вручную; автоподстановка lat/lng по адресу не требуется |
| `DELETE /bookings/{id}` | В MVP не используется; отмена через `PATCH …/cancel` |
| Прочие роли кроме `CLIENT` / `ADMIN` | Не проверять multi-tenant, manager и т.п. |
| Прод-хардening вне спецификации | CDN, WAF, multi-replica, managed DB — вне AC, если не описаны в MVP |

**Не путать с AC:** отсутствие функции из таблицы выше — норма; отсутствие UC-01…UC-20 или инвариантов AC-02…AC-14 — дефект приёмки.

## 9.6. Быстрый сценарий demo (30–40 мин)

Рекомендуемый порядок для защиты/демо (после AC-11):

1. Seed login CLIENT + ADMIN.

6. Показать зелёный CI + coverage report + README cold-start (AC-12…14).
